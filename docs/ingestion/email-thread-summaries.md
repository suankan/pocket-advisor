# Email-Thread Summaries

Status: **implemented and locked** (this document consolidates the design
already shipped across `docs/ingestion/chunking-and-embedding.md` decisions
3–6, the summary stage, `docs/ingestion/summary-generation-concurrency.md`,
and `docs/inference/inference-serving.md` decisions 11–12). Written
2026-07-23 to explain in one place what email-thread summaries are, why
they exist, how they are produced and consumed — and to carry the open
TODOs at the bottom, which came out of the 2026-07-23 architecture review
that questioned whether ingest-time summaries should exist at all.

These are **email**-thread summaries, and nothing else: threads are
reconstructed exclusively from email headers (JWZ over
Message-ID/References plus the subject/participant fallback), and summary
eligibility is literally `COUNT(emails in thread) >= 2` — documents never
form threads and are never summarized. The doc was renamed from
`thread-summaries.md` on 2026-07-23 to make that explicit; TODO 3 below
extends the same disambiguation into the code.

## What they are

One generated navigation summary per **multi-email thread** (two or more
email items). Singleton threads — the majority of the corpus — have no
summary and pay no generative cost; their leaf chunks carry them. A summary
is a bounded (600-token ceiling), chronological, factual digest generated by
the configured `summarisation_endpoint` under `SUMMARY_PROMPT_VERSION=2`,
which explicitly asks for early, middle, and late turning points so the
final messages cannot dominate.

Stored as one `thread_summaries` row (summary text, `source_digest`,
`prompt_version`, `is_stale`), indexed twice: `thread_summaries_fts` for
BM25 and a dedicated dense namespace
(`vectors/text/<fingerprint>/threads/`) whose vector filenames bind
`thread_id` to a hash of the summary text, so a changed summary can never
reuse a stale vector.

## Why they exist

Leaf chunks are message-grained. A long negotiation thread's *meaning* —
what was proposed, conceded, and left unresolved across months — lives at
thread grain, spread over dozens of messages none of which states it. The
summary gives retrieval a second, thread-grained recall channel for
queries like "what was agreed about the school holidays", where no single
message chunk ranks well but the thread as a whole is obviously the
answer.

Two design fences keep this channel from polluting content retrieval:

1. **Separate namespace, fused late.** Summary FTS and summary dense are
   their own two RRF legs beside the two leaf legs — own matrix, own FTS
   table. They compete for *thread selection*, not for passage ranking,
   and per-item dedup keeps the best evidence regardless of channel.
2. **Navigation, never content** (system invariant 6, `docs/design.md`).
   A summary hit is labeled `THREAD(sum)`, is never a citation target,
   and the packet it selects contains the real readable messages. The
   future answering pass may use summaries only to navigate.

## How they are produced (ingest-time lifecycle)

- **Staleness is unconditional; generation is gated.** Every `ingest all`
  run recomputes each eligible thread's `source_digest` (stable thread key
  + ordered Message-IDs, timestamps, and readable body bytes) and marks
  divergent rows `is_stale=1` — even when `ingestion.summarize_threads`
  is false. The knob gates only the generative pass, so retrieval can
  never serve a summary whose sources silently diverged. Stale summaries
  are excluded from both retrieval legs and from embedding.
- **Only changed threads regenerate.** A new email invalidates exactly its
  own thread's summary; the other N−1 threads' digests match and are
  skipped. Generation runs up to `INFERENCE_MAX_IN_FLIGHT` (8) threads
  concurrently through `EmailThreadsSummaryDispatcher`.
- **Bounded strategies.** One-shot generation up to the quality-tested
  48,000-estimated-token ceiling; above it, 24,000-token chronological
  segments reduced through a fixed 16-way tree; an individually oversized
  message uses exact reconstructable slices. No path silently truncates.
- **Failure is non-blocking.** A failed generation review-flags, keeps the
  previous row stale (excluded), and retries next run.

The ingest-time summary is best understood as a **content-addressed
memoization of runtime summarization**: the digest is the cache key, the
thread's readable artifacts are the input, and the cost is paid once per
content change instead of once per query.

## How they are consumed

- `run_search` runs four legs; the two summary legs are visible only for
  threads whose *every* member is visible through the selected workspace
  mounts (whole-thread visibility).
- The accuracy suite's verdict ladder has a dedicated `THREAD(sum)`
  outcome: the expected thread was selected *via the summary channel*.
  This is the built-in instrument for measuring whether the channel earns
  its keep (see TODO 2).

## Known concerns (recorded 2026-07-23, operator review)

1. **Recompute-on-arrival cost.** Real but bounded: digest convergence
   limits it to changed threads, and generation is 8-wide concurrent.
2. **Multi-topic dilution.** A long thread spans topics; compressing it
   into one summary (and one vector) blends them. The two-namespace fences
   above contain the blast radius — a diluted summary can only fail to
   *add* recall, not corrupt leaf ranking — but whether the channel adds
   net value on this corpus is an empirical question, not a settled one.
3. **Runtime alternative.** Summarization could instead be an on-demand
   capability of the retrieval engine (query densification before search,
   result shaping after). That is a complement with different latency
   economics — per-query decode in the user's critical path versus
   once-per-change at ingest — not a drop-in replacement.

The decision standard: **the summary channel stays exactly as long as
measurement says it helps; intuition in either direction doesn't count.**

## TODO 1 — Runtime summarization methods on the retrieval engine

Add on-demand summarization as first-class interface methods of the
retrieval engine / Corpus API (`docs/retrieval/corpus-api.md`), independent
of the ingest-time index:

- **Query-side**: densify/classify the user's question before vector
  search (a `generate()` call producing a tighter search query or
  sub-queries).
- **Result-side**: summarize/shape retrieved packets on request. Note:
  shaping a final answer in the user's register belongs to the generation
  pipeline (`docs/generation/local-answering-pass.md`); the retrieval
  engine exposes the mechanism, the answering pass owns the policy.

These methods reuse `InferenceClient.generate()` and must respect the
untrusted-content prompt rules and the navigation-not-content invariant.

## TODO 2 — Summary-ablation accuracy methodology

Extend the accuracy harness to measure, specifically, whether the
ingest-time summary channel improves retrieval and user experience:

- **Ablation mode**: run the identical expectation suite with the two
  summary legs disabled (config or `accuracy run` flag), against the same
  index, and diff verdicts via `accuracy compare`. The decisive statistic
  is the count of questions that are `THREAD(sum)`-or-better *only* with
  the channel enabled, and any `STRONG`→`MISS` regressions it causes.
- **Targeted question class**: current generated questions are
  single-passage-anchored, which structurally under-tests thread-grain
  recall. Add a generated (or hand-authored) question class anchored on
  *cross-message* facts — things stated by no single message — with
  `expect_thread_key` anchors, where summaries should shine if they shine
  at all.
- **Experience dimension**: record per-question latency deltas (the
  summary legs' query-time cost is near zero; the honest comparison is
  against the TODO-1 runtime alternative, whose per-query decode cost
  must be measured on the same hardware).
- Outcome rule: if the ablation shows no `THREAD(sum)`-only wins on both
  the standard and the new thread-grain suites, retire the ingest-time
  summary index (staleness machinery and all) in favor of the runtime
  methods; if it shows wins, keep both and record the numbers here.

## TODO 3 — Rename "thread" → "email_thread" across the code

The codebase uses "thread" for two unrelated things: the email-conversation
concept (this document) and Python threading (`ThreadPoolExecutor` pools in
the PDF stage, `EmbedDispatcher`, `EmailThreadsSummaryDispatcher`,
`threading.Event` interrupt handling). Reading `thread_id` next to a worker
pool forces the reader to disambiguate every time. Rename the
email-conversation sense to `email_thread` throughout; Python threading
keeps the unqualified word.

Scope (mechanical but wide — survey before executing):

- **Database**: `threads`, `thread_summaries`, `thread_summaries_fts`,
  `emails.thread_id`, `thread_link_method`. A schema rename is a
  fresh-schema cutover under the engine's rules: wipe + re-ingest, no
  migration shims.
- **CLI/config**: the `ingest thread` stage name, `query --thread`,
  `thread_fallback_window_days`, `summarize_threads`,
  `thread_summary_max_tokens`, `thread_context_chars` — old spellings
  rejected as deprecated keys per the no-alias convention.
- **Code**: `modules/pipeline/thread.py` / `ThreadStage`, `_ThreadWork`,
  `thread_vector_filename`, the `threads/` vector namespace directory,
  retrieval's thread legs/packets, daemon status fields.
- **Caution — preserved user data**: the accuracy schema's
  `expect_thread_key` lives in hand-authored, wipe-surviving expectation
  YAML. Renaming that key must either keep loader compatibility for the
  old spelling (contrary to the no-alias convention) or come with an
  explicit one-time operator migration of the preserved suites; decide
  deliberately, don't break test data silently.
- Verdict labels `THREAD` / `THREAD(sum)` and result-record JSON fields
  are part of saved accuracy records; renaming them bumps the result
  schema version.
